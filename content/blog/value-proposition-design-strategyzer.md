Ask most founders to describe their value proposition and you'll get a features list. Ask them to describe their customer's problem in the customer's own words, and the conversation gets noticeably harder — which is usually the tell that the value proposition was designed backward, from the product outward, instead of forward, from the customer in.

Strategyzer's Value Proposition Canvas — the tool behind the *Value Proposition Design* methodology — forces the second conversation to happen before the first one is allowed to matter.

## Two sides, filled out in order

The canvas has two halves, and the discipline is in not skipping to the right-hand side.

**The Customer Profile (fill this out first):**
- **Jobs** — what the customer is actually trying to get done, functionally, socially, and emotionally. Not "wants a project management tool" but "needs to prove to their manager that a cross-team initiative is on track."
- **Pains** — what makes that job frustrating, risky, or costly today.
- **Gains** — what outcome, beyond just "job done," the customer would consider a genuine win.

**The Value Map (fill this out second, against the profile — not independently):**
- **Products & Services** — what's actually being offered.
- **Pain Relievers** — specifically how each offering addresses a named pain.
- **Gain Creators** — specifically how each offering produces a named gain.

The point of the exercise isn't the canvas itself; it's the discipline of refusing to write anything in the Value Map until the Customer Profile is grounded in real evidence — interviews, observed behavior, support tickets — rather than assumption.

## Fit is a claim, not a feeling

"Product-market fit" gets treated as something you either have or don't, discovered by intuition after launch. Value Proposition Design treats fit as a specific, checkable claim: *for this named job, this pain reliever addresses this named pain, and here's the evidence that the pain is real and severe enough that customers will pay to relieve it.* That claim can be tested before a single line of production code is written — often with the same interview and prototype techniques used in a Design Sprint.

## Where this fails without discipline

The exercise is easy to run badly. Two failure modes come up constantly:

1. **Writing the Value Map first, then reverse-engineering a Customer Profile that justifies it.** This produces a canvas that looks complete and validates nothing, because the "customer research" was really just confirmation of a decision already made.
2. **Treating one canvas as permanent.** A value proposition that fit a customer segment a year ago may not fit it today — markets move, and a canvas is a snapshot, not a certificate.

## Why we pair this with Lean Startup and Design Sprints

Value Proposition Design answers *what should we offer, and to whom.* Lean Startup's Build-Measure-Learn loop and the Design Sprint format then answer *how do we test that fast, before spending real engineering budget.* Run in sequence — canvas first, sprint second — a founding team can go from an untested hypothesis about customer value to evidence, in the time it used to take just to write the pitch deck.
